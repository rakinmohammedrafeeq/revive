## Reporting a Vulnerability

We take the security of Ledgera seriously. If you believe you have found a security vulnerability, please report it to us as described below.

### Please Do Not

* **Open a public GitHub issue** for security vulnerabilities
* **Discuss the vulnerability publicly** until it has been addressed

### Please Do

**Report security vulnerabilities by emailing:** [your-email@example.com]

Please include the following information:

* **Type of vulnerability** (e.g., SQL injection, XSS, authentication bypass)
* **Full paths of source files** related to the vulnerability
* **Location of the affected source code** (tag/branch/commit or direct URL)
* **Step-by-step instructions to reproduce** the issue
* **Proof-of-concept or exploit code** (if possible)
* **Impact of the vulnerability** and how an attacker might exploit it
* **Your name/handle** for acknowledgment (optional)

### What to Expect

* **Acknowledgment**: We will acknowledge receipt of your vulnerability report within 48 hours
* **Communication**: We will keep you informed about our progress in addressing the vulnerability
* **Timeline**: We aim to patch critical vulnerabilities within 7 days, high severity within 30 days
* **Credit**: We will credit you in our security advisory (unless you prefer to remain anonymous)
* **Disclosure**: We follow coordinated disclosure practices

## Security Best Practices for Users

### Environment Variables

Never commit sensitive information to the repository:

* Database credentials
* API keys (Groq, Gemini, OpenAI)
* JWT secrets
* Email service credentials
* OAuth client secrets

Use `.env` files locally and environment variables in production.

### Database Security

* Use strong database passwords (minimum 16 characters)
* Enable SSL/TLS for database connections in production
* Restrict database access to application servers only
* Regularly backup your database
* Keep PostgreSQL updated to the latest stable version

### Application Security

* Use HTTPS in production (never HTTP)
* Keep dependencies updated regularly
* Use strong JWT secrets (minimum 32 characters)
* Implement rate limiting for API endpoints
* Enable CORS only for trusted domains
* Use secure session management

### Authentication

* Enforce strong password policies (minimum 8 characters, mixed case, numbers, special chars)
* Enable two-factor authentication (OTP via email)
* Implement account lockout after failed login attempts
* Use secure password hashing (BCrypt with appropriate work factor)
* Rotate JWT tokens regularly
* Implement refresh token rotation

### Authorization

* Follow principle of least privilege
* Validate user permissions on every request
* Use role-based access control (RBAC)
* Verify workspace membership before data access
* Implement proper API authorization

### Input Validation

* Validate all user inputs on both client and server
* Sanitize data before storing in database
* Use parameterized queries to prevent SQL injection
* Implement Content Security Policy (CSP)
* Validate file uploads (type, size, content)

### API Security

* Implement rate limiting (currently 100 requests/minute per user)
* Use API versioning for backward compatibility
* Log security-relevant events
* Implement request signing for sensitive operations
* Use HTTPS for all API communications

### Frontend Security

* Implement Content Security Policy
* Use secure cookies (HttpOnly, Secure, SameSite)
* Sanitize user-generated content before rendering
* Avoid storing sensitive data in localStorage
* Implement proper error handling without exposing system details

### Third-Party Services

* Review third-party dependencies regularly
* Use official SDKs from trusted sources
* Keep API keys separate for development and production
* Monitor API usage and set spending limits
* Use read-only keys when possible

## Known Security Considerations

### AI Services

* AI responses are generated by third-party services (Groq, Gemini)
* User financial data is sent to AI providers for processing
* Implement data anonymization where possible
* Review AI provider terms of service and privacy policies

### Database Vector Search

* pgvector extension is required for AI features
* Embedding data contains semantic representations of financial records
* Consider encryption at rest for sensitive embeddings

### OAuth Integration

* OAuth tokens are stored securely in the database
* Implement token refresh mechanisms
* Validate OAuth state parameters
* Use PKCE (Proof Key for Code Exchange) for public clients

## Compliance

### Data Protection

* **GDPR**: Users can request data export and deletion
* **CCPA**: California residents have additional privacy rights
* **Financial Data**: Follow PCI DSS guidelines if processing payment card data

### Audit Logging

* Log authentication attempts (success and failure)
* Log authorization decisions
* Log data access and modifications
* Retain logs according to compliance requirements

## Security Updates

We regularly update dependencies to address security vulnerabilities:

```bash
# Backend security updates
cd backend
./mvnw versions:display-dependency-updates

# Frontend security updates
cd frontend
npm audit
npm audit fix
```

## Security Checklist for Deployment

- [ ] All environment variables are set securely
- [ ] Database uses strong password and SSL/TLS
- [ ] HTTPS is enabled with valid certificates
- [ ] JWT secret is strong and unique
- [ ] Rate limiting is configured
- [ ] CORS is restricted to trusted domains
- [ ] Security headers are configured (CSP, HSTS, X-Frame-Options)
- [ ] Database backups are automated
- [ ] Logging and monitoring are enabled
- [ ] Error messages don't expose system details
- [ ] API keys have spending limits
- [ ] File upload restrictions are in place
- [ ] Session timeout is configured appropriately
